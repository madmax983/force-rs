# 🔭 Vantage: Spec for Zod Schema Generator

**Business problem:**
Enterprise teams building modern TypeScript applications (React, Node.js, Next.js) that interact with Salesforce data often suffer from the "TypeScript Illusion." While static type interfaces (like those generated by the TypeScript Interface Generator) provide compile-time safety, they offer zero protection at runtime when data actually arrives from the Salesforce API. If a Salesforce administrator changes a field type, adds a new required field, or drops a field without updating the frontend, the application can fail unpredictably at runtime. We need a way to validate incoming Salesforce payloads at the boundary.

**Gap Analysis:**
Currently, developers must manually write and maintain runtime validation schemas (using libraries like Zod, Joi, or Yup) that mirror their Salesforce SObjects. This double-bookkeeping (maintaining both Salesforce schema and Zod schema) is tedious, prone to human error, and rarely kept in sync with the live Org metadata. There is no automated tool to directly translate `SObjectDescribe` payloads into robust Zod runtime validation schemas.

**Success metric:**
Success = Ability to generate a syntactically correct, executable Zod schema (e.g., `export const AccountSchema = z.object({ ... });`) for a complex SObject like `Account` or `Contact` with 100+ fields in under 1 second. The generated schema must successfully parse valid SObject JSON payloads and reject invalid ones with precise error paths.

👤 **User Story:**
As a Full-Stack or Frontend Developer, I want to automatically generate Zod validation schemas from Salesforce object metadata, so that I can validate incoming API payloads at runtime, ensuring data integrity before it enters my application's business logic, without manually writing schema definitions.

✅ **Acceptance Criteria:**
- Must map standard Salesforce field types to standard Zod types (e.g., `z.boolean()`, `z.number()`, `z.string()`).
- Must correctly represent optional (nillable) fields using `.nullable()` or `.optional()`.
- Must apply string length constraints (using `.max()`) based on the Salesforce field's `length` metadata.
- Must include JSDoc comments or inline comments indicating the Salesforce field label or help text where appropriate.
- Must sort fields alphabetically for predictable output, with the `Id` field always appearing first.
- The output should export the schema (e.g., `export const AccountSchema = ...`).

🚫 **Out of Scope:**
- Generating validation schemas for child relationships or deeply nested SOQL queries in the initial phase.
- Implementing custom Zod refinements `.refine()` for complex cross-field validation rules.
- Supporting validation libraries other than Zod (e.g., Yup, Joi).
